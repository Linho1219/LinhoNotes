# 2.4 值语义、复制与移动

`int` 很容易理解：把一个整数赋给另一个整数后，两边是相互独立的值。

```cpp
int first{42};
int second = first;
second = 10;
// first 仍然是 42
```

设计自己的类型时，也要决定复制、赋值和销毁究竟意味着什么。现代 C++ 倾向于让普通类型具有自然的**值语义**：对象代表一个值，复制后得到相等但可以独立修改的对象。

## 标准库成员已经知道怎样复制

考虑第一章使用的学生：

```cpp
struct Student {
    int id{};
    std::string name;
    Score score;
};
```

编译器会为它生成逐成员复制操作：`int` 和 `Score` 被复制，`std::string` 也复制自己的文本。

```cpp
Student first{1001, "Alice", Score{85}};
Student second = first;
second.name = "Bob";

// first.name 仍然是 "Alice"
```

`std::string` 内部可能使用动态内存，但它已经正确实现资源管理和复制。`Student` 不需要知道这些细节。

## 特殊成员函数

C++ 中有几种负责对象创建、复制、移动和销毁的特殊成员函数：

```cpp
class Example {
public:
    Example();                            // 默认构造函数
    Example(const Example& other);        // 复制构造函数
    Example& operator=(const Example&);   // 复制赋值运算符
    Example(Example&& other) noexcept;    // 移动构造函数
    Example& operator=(Example&&) noexcept; // 移动赋值运算符
    ~Example();                           // 析构函数
};
```

复制构造用于创建新对象，复制赋值用于替换已经存在的对象：

```cpp
Example first;
Example second = first; // 复制构造

Example third;
third = first; // 复制赋值
```

在满足规则时，编译器会隐式声明或定义这些操作。我们通常应让成员类型各自管理自己，而不是立即手写全部函数。

## 先记住 Rule of Zero

Rule of Zero（零法则）是现代类设计最重要的默认选择：

> 如果类的成员都能正确管理自身资源，就不要自己定义析构、复制和移动操作。

```cpp
#include <string>
#include <utility>
#include <vector>

class GradeBook {
public:
    void add(Student student) {
        students_.push_back(std::move(student));
    }

private:
    std::string course_name_;
    std::vector<Student> students_;
};
```

`string` 和 `vector` 已经实现了正确的特殊成员函数，因此 `GradeBook` 默认就可以安全复制、移动和销毁。这正是组合资源管理类型的价值。

## 一个裸指针怎样破坏复制

下面是一个故意写坏的动态数组包装：

```cpp
class BadBuffer {
public:
    explicit BadBuffer(std::size_t size)
        : size_{size}, data_{new int[size]} {}

    ~BadBuffer() {
        delete[] data_;
    }

private:
    std::size_t size_{};
    int* data_{};
};
```

它的析构函数能够释放内存，但默认复制只会逐成员复制指针：

```cpp
BadBuffer first{100};
BadBuffer second = first;
```

两个对象的 `data_` 指向同一块内存，析构时会重复 `delete[]`。如果想让它具有值语义，就必须深复制元素；如果不允许复制，就必须明确删除复制操作。

更好的业务代码通常直接使用：

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t size) : data_(size) {}

private:
    std::vector<int> data_;
};
```

它回到了 Rule of Zero。

## Rule of Five 是底层资源类型的提醒

如果一个类确实直接管理资源，并且需要自定义析构、复制或移动，那么另外几种操作往往也需要一起审视。这称为 Rule of Five（五法则），不是要求每个类都机械写五个函数。

需要问的问题包括：

- 复制是深复制、共享资源，还是应被禁止？
- 赋值前如何处理目标对象已经拥有的资源？
- 移动后，源对象怎样保持可析构、可赋值？
- 自赋值是否安全？
- 某一步失败时，原对象是否仍然有效？

如果只是希望禁止复制，可以显式写出：

```cpp
class Session {
public:
    Session() = default;

    Session(const Session&) = delete;
    Session& operator=(const Session&) = delete;

    Session(Session&&) noexcept = default;
    Session& operator=(Session&&) noexcept = default;

private:
    std::unique_ptr<Resource> resource_;
};
```

`= delete` 表示该操作不允许使用，`= default` 表示要求编译器生成默认实现。这个示例假设 `Resource` 是已经定义的资源类型。

## 移动不是更快的复制

复制通常保留源对象的值，移动则允许从源对象转移资源：

```cpp
#include <string>
#include <utility>

std::string source{"A potentially long string"};
std::string target{std::move(source)};
```

`std::move` 本身不移动任何东西。它只是把表达式转换成允许选择移动操作的形式，真正的移动由 `std::string` 的移动构造函数完成。

移动也不保证一定比复制快：

- 对 `int` 之类的类型，移动和复制没有区别；
- 某些对象没有移动操作，最终仍会复制；
- `const` 对象通常不能把资源交出去，`std::move` 后也可能调用复制；
- 一些带特殊分配器或内部约束的类型，移动赋值可能仍需处理元素。

因此不要为了显得现代而到处添加 `std::move`。它表达的是「后续不再依赖这个值，可以让接收者取走其资源」。

## 移动后的对象仍然存在

对标准库类型进行移动后，源对象通常处于「有效但值未指定」的状态。对象仍然可以析构，也可以执行不依赖当前值的操作，例如重新赋值；但不能假设它一定为空。

```cpp
std::string source{"Alice"};
std::string target{std::move(source)};

source = "Bob"; // 合法：为移动后的对象赋予新值
```

不要写依赖 `source.empty()` 必然为真的逻辑。个别类型会给出更强保证，例如移动后的 `unique_ptr` 为空；应以具体类型的契约为准。

## 返回局部对象不需要手工移动

```cpp
Student make_student() {
    Student result{1001, "Alice", Score{85}};
    return result;
}
```

这里编译器可以通过返回值优化直接在调用者的位置构造 `result`；即使没有进行复制消除，也可以选择移动。写成 `return std::move(result);` 反而可能阻碍某些复制消除，不应作为默认写法。

同样，按值接收后保存参数是一种简单实用的接口：

```cpp
class StudentRecord {
public:
    explicit StudentRecord(std::string name)
        : name_{std::move(name)} {}

private:
    std::string name_;
};
```

调用者传入临时字符串时可以移动，传入已有字符串时先复制到参数，再移动到成员。是否需要为极致性能增加 `const&` 与 `&&` 两个重载，应在测量和确有需求后决定。

## `noexcept` 为什么常出现在移动操作上

一些容器在重新分配时，需要在「移动旧元素」和「复制旧元素」之间选择。如果移动构造可能抛出异常，而复制可用，容器可能选择复制，以便在失败时保留原有元素。

因此，一个确实不会失败的自定义移动操作通常应声明为 `noexcept`。但这必须是真实保证；如果成员的移动可能抛出，就不能为了性能谎称不会抛出，否则异常逃出时程序会调用 `std::terminate`。

使用 Rule of Zero 时，编译器会根据成员类型推导默认移动操作的异常说明，通常不需要手工干预。

## 小结

- 值语义让复制后的对象相等但彼此独立
- 标准库资源类型可以组合出正确的默认复制与移动
- 优先遵循 Rule of Zero，不要机械实现特殊成员函数
- 直接管理资源时，析构、复制和移动必须一起审视
- `std::move` 只是允许选择移动操作，不会自行移动
- 移动不保证更快，移动后的值也不一定为空
- 返回局部对象时直接 `return result`
- 只有能兑现保证时才把移动操作声明为 `noexcept`
