# 3.5 让工具替你抓虫

C++ 允许程序员直接管理内存、对象生命周期和底层表示，也意味着许多错误不会自动变成清楚的运行时异常。好消息是，编译器和周边工具已经知道大量常见错误模式。项目应当让这些工具持续工作，而不是只在代码失控后偶尔运行一次。

不同工具观察的层面不同：

```text
编译警告 -> 不运行程序就能发现的可疑代码
静态分析 -> 跨越更多语义规则分析源码
调试器   -> 暂停一次真实执行并观察状态
sanitizer -> 在真实执行中捕获被插桩的非法行为
测试     -> 检查业务结果是否符合预期
```

它们互相补充，没有哪一个能单独证明程序正确。

## 首先认真对待编译警告

在 GCC 和 Clang 下，可以从这组警告开始：

```sh
-Wall -Wextra -Wpedantic
```

名字中的 `-Wall` 并不是真的打开所有警告，只是一组广泛使用的基础警告。MSVC 中相近的起点是 `/W4 /permissive-`。

上一节已经把选项附着到各个 CMake 目标：

```cmake
function(enable_project_warnings target_name)
    if(MSVC)
        target_compile_options(${target_name} PRIVATE /W4 /permissive-)
    else()
        target_compile_options(${target_name} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endfunction()
```

目标应当在正常开发中保持无警告。不要看到警告就机械地强制转换、加 `(void)` 或全局关闭规则；先理解工具认为哪里可疑。确认是有意行为后，才在最小范围内表达或抑制。

把警告视为错误的 `-Werror` 或 `/WX` 很适合 CI 中的项目自身代码，但不宜无条件传播给使用你的库的人，也可能需要避开第三方头文件。编译器升级会新增警告，因此“CI 零警告”还需要稳定的工具链版本和维护。

## Debug 与 Release 不是“能调试”和“不能调试”

常见 CMake 构建类型大致有这些差异：

| 构建类型        | 优化              | 调试信息          | 常见用途         |
| --------------- | ----------------- | ----------------- | ---------------- |
| `Debug`         | 低或关闭          | 完整              | 日常调试与检查   |
| `Release`       | 较高              | 通常较少或无      | 发布与性能测量   |
| `RelWithDebInfo`| 较高              | 保留               | 接近发布环境排错 |

具体选项由生成器和工具链决定，不要仅凭名称假设全部细节。

优化会改变指令顺序、内联函数，甚至移除变量，因此 Release 下单步执行可能不再严格对应源码顺序。但程序在不同优化级别下得到不同业务结果，往往意味着未定义行为、未初始化读取、竞态或错误地依赖 `assert` 的副作用，而不是“编译器把正确代码优化坏了”。

测试 Debug 和 Release 都有价值。性能测量则应使用优化构建，否则结论没有代表性。

## 用调试器回答具体问题

调试器最适合验证一个假设，例如“进入这个函数时 `count` 已经变成负数了吗”，而不是漫无目的地逐行走完整个程序。

使用 GCC 工具链时，可以用 GDB 启动 Debug 构建：

```sh
gdb ./build/debug/grades_app.exe
```

一组最基本的命令如下：

| 命令                     | 作用                         |
| ------------------------ | ---------------------------- |
| `break main`             | 在 `main` 入口设置断点       |
| `break file.cpp:42`      | 在指定源码行设置断点         |
| `run`                    | 启动或重新启动程序           |
| `next`                   | 执行当前行，不进入被调函数   |
| `step`                   | 执行当前行，进入被调函数     |
| `continue`               | 继续到下一个断点或程序结束   |
| `print expression`       | 计算并显示表达式             |
| `backtrace`              | 显示当前调用栈               |
| `frame n`                | 切换到调用栈中的某一帧       |
| `quit`                   | 退出                         |

IDE 中的断点、单步、变量窗口和调用栈，底层提供的是同类能力。遇到崩溃时，调用栈通常比最后一行错误信息更有价值：崩溃点说明症状发生在哪里，较上层调用者可能解释坏状态怎样一路传来。

观察变量也可能改变程序时序，尤其是多线程程序。调试器看到的是一次执行的状态，不是对所有输入的证明。

## AddressSanitizer 查找内存错误

AddressSanitizer（ASan）通过编译期插桩，在运行时发现许多内存问题，例如：

- 堆、栈和全局对象的越界访问；
- 释放后继续使用；
- 重复释放；
- 部分平台上的内存泄漏。

使用 GCC 或 Clang 时，最小命令类似：

```sh
g++ -std=c++20 -g -O1 -fsanitize=address -fno-omit-frame-pointer buggy.cpp
./a.exe
```

发现问题后，ASan 会给出错误类别、访问位置以及分配或释放位置。首先修复报告中的第一个问题；后续错误可能只是内存已经被破坏后的连锁反应。

ASan 有运行时和平台限制。例如泄漏检测并非在所有 Windows 配置中都受支持。应以当前编译器文档和实际工具链能力为准，不能把“没有报告”理解为“绝对没有内存错误”。

## UndefinedBehaviorSanitizer 查找未定义行为

UndefinedBehaviorSanitizer（UBSan）能捕获一部分未定义行为，例如有符号整数溢出、某些越界移位、空指针或未对齐访问：

```sh
g++ -std=c++20 -g -O1 -fsanitize=undefined -fno-omit-frame-pointer buggy.cpp
./a.exe
```

在工具链支持时，可以组合：

```sh
-fsanitize=address,undefined
```

sanitizer 只有在相关路径真正运行时才可能报告，所以应当让测试套件运行插桩后的构建。它也并不覆盖所有未定义行为；静态分析和代码审查仍然必要。

## 在 CMake 中显式开启 sanitizer

可以给项目添加一个选项，并对自己的目标应用设置：

```cmake
option(ENABLE_SANITIZERS "Enable AddressSanitizer and UBSan" OFF)

function(enable_sanitizers target_name)
    if(NOT ENABLE_SANITIZERS)
        return()
    endif()

    if(CMAKE_CXX_COMPILER_ID MATCHES "Clang|GNU")
        target_compile_options(${target_name} PRIVATE
            -fsanitize=address,undefined
            -fno-omit-frame-pointer
        )
        target_link_options(${target_name} PRIVATE
            -fsanitize=address,undefined
        )
    else()
        message(WARNING "Sanitizer options are not configured for this compiler")
    endif()
endfunction()

enable_sanitizers(grades_core)
enable_sanitizers(grades_app)
```

测试可执行文件也应调用这个函数。包含插桩代码的静态库和最终可执行文件都要使用兼容设置，最终链接步骤尤其需要链接 sanitizer 运行时。

可以在 preset 中派生一个配置：

```json
{
  "name": "asan",
  "inherits": "debug",
  "binaryDir": "${sourceDir}/build/asan",
  "cacheVariables": {
    "ENABLE_SANITIZERS": "ON"
  }
}
```

工具链对 sanitizer 的支持会随操作系统和编译器版本不同。配置失败时应查对应编译器的官方支持情况，不要为了让命令通过而盲目删除链接选项。

## `clang-tidy` 做静态分析

`clang-tidy` 基于 Clang 的语义信息检查源码，可以发现可疑写法、现代化机会、性能问题和部分易错接口。项目根目录可以创建 `.clang-tidy`：

```yaml
Checks: >
  -*,
  bugprone-*,
  performance-*,
  readability-*,
  modernize-*
WarningsAsErrors: ''
HeaderFilterRegex: '^(include|src)/'
```

这只是一个起点。一次打开过多规则会产生大量噪声，而且有些规则与项目风格冲突。应逐步启用、理解规则，再决定修复或局部禁用。

CMake 配置时可指定：

```sh
cmake --preset debug -DCMAKE_CXX_CLANG_TIDY=clang-tidy
cmake --build --preset debug
```

也可以在 `CMakeLists.txt` 中只给某些目标设置 `CXX_CLANG_TIDY` 属性。上一节 preset 打开的 `CMAKE_EXPORT_COMPILE_COMMANDS` 会生成 `compile_commands.json`，其中记录每个翻译单元的真实编译命令，许多编辑器和分析工具都依赖它。

`clang-tidy` 的自动修复很方便，但不能替代审阅。工具可能改变接口、性能特征或代码意图，应用修复后仍要查看 diff、重新构建并运行测试。

## `clang-format` 统一排版

格式化工具解决空格、换行和括号位置等机械争论。项目根目录的 `.clang-format` 保存共同规则：

```yaml
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
```

检查单个文件的格式差异：

```sh
clang-format --dry-run --Werror src/main.cpp
```

就地格式化：

```sh
clang-format -i src/main.cpp
```

格式化器不判断命名是否清楚、抽象是否合理，也不会修复 bug。它的价值是把低价值的排版选择自动化，让评审集中在行为和设计上。

最好在项目较早阶段确定规则。对历史大型项目一次性重排所有文件，会制造巨大 diff，也会干扰 `git blame`；可以单独提交格式化，或只格式化本次改动范围。

## 建立一条本地反馈链

日常开发可以形成固定顺序：

```text
编辑 -> 格式化 -> 编译警告 -> 单元测试 -> 静态分析 -> sanitizer 测试
```

最快的检查放在前面，耗时检查可以在提交前或 CI 中完整执行。出现失败时保留工具原始报告，并从第一个明确问题开始处理，不要用关闭规则或捕获所有异常让流水线“变绿”。

## 小结

- 高警告等级应成为项目默认配置，警告需要理解而不是机械消音
- Debug、Release 和 RelWithDebInfo 的差别主要在优化与调试信息，不能掩盖代码语义错误
- 调试器用断点、单步、变量和调用栈观察一次真实执行
- ASan 检测许多内存错误，UBSan 检测一部分未定义行为
- sanitizer 必须运行到问题路径才会报告，应与测试套件配合
- `clang-tidy` 分析语义规则，`clang-format` 统一机械排版
- 工具各自覆盖不同风险，应组成持续而快速的反馈链
