# 3.3 错误不是打印一句话然后退出

小程序常在发现问题后立即输出一句话并退出：

```cpp
if (score < 0 || score > 100) {
    std::cerr << "Invalid score\n";
    return 1;
}
```

但库函数不应擅自决定错误显示成中文还是英文，也不应决定整个进程是否退出。随着项目分层，发现错误的位置、补充上下文的位置、记录日志的位置和最终向用户说明的位置往往并不相同。

错误处理的目标不是选出一种“最现代”的语法，而是建立一条清晰的失败路径。

## 先区分发生了什么

面对异常情况，可以先把它归入几类。

### 前置条件被违反

函数的前置条件描述调用者必须满足的要求。例如索引必须位于范围内、传入的指针不能为空。若只有程序员写错代码才会违反它，这通常是程序缺陷，而不是一次可恢复的用户输入错误。

```cpp
#include <cassert>
#include <span>

int element_at(std::span<const int> values, std::size_t index) {
    assert(index < values.size());
    return values[index];
}
```

`assert` 在条件为假时终止程序，适合检查开发期间“不应该发生”的内部假设。它可能在定义 `NDEBUG` 的构建中被移除，因此：

- 不要用 `assert` 校验用户输入、网络数据或文件内容；
- 不要把必须执行的操作放进 `assert` 表达式；
- 不要指望调用者捕获断言失败并继续运行。

如果无效值来自正常外部输入，它就不是调用者程序的 bug，应使用正常的错误通道。

### 正常的缺失

查找学生时“没有这个学号”可能是预期结果，而且调用者不关心更详细的原因。此时 `std::optional<Student>` 很合适：

```cpp
std::optional<Student> find_student(std::span<const Student> students,
                                    int id);
```

`optional` 只有“有”和“没有”两种状态。若失败原因会影响后续决定，就需要更丰富的类型。

### 可预期且需要说明的失败

解析输入可能因为不是整数，也可能因为超出范围。这些情况并不稀奇，调用者通常要分别显示提示或继续询问。

C++23 的 `std::expected<T, E>` 同时保存成功值 `T` 或错误值 `E`：

```cpp
#include <charconv>
#include <expected>
#include <string_view>

enum class ScoreError {
    not_an_integer,
    out_of_range,
};

std::expected<Score, ScoreError> parse_score(std::string_view text) {
    int value{};
    const auto [end, error] =
        std::from_chars(text.data(), text.data() + text.size(), value);

    if (error != std::errc{} || end != text.data() + text.size())
        return std::unexpected{ScoreError::not_an_integer};

    const auto score = Score::from(value);
    if (!score)
        return std::unexpected{ScoreError::out_of_range};

    return *score;
}
```

调用者必须显式面对两条路径：

```cpp
const auto result = parse_score(text);
if (!result) {
    show_score_error(result.error());
    return;
}

save_score(*result);
```

`std::expected` 属于 C++23。本系列仍以 C++20 为主线时，可以使用成熟的兼容实现、项目自定义结果类型，或依据项目约定使用异常。重要的是语义：失败是接口的一部分，错误类型应让调用者作出决定。

错误类型优先表达机器可处理的事实，而不是过早拼出面向最终用户的句子。`ScoreError::out_of_range` 可以在命令行中变成英文，在图形界面中变成中文，也可以被测试稳定比较。

### 无法在当前层合理处理的失败

有些操作失败后无法返回一个有意义的局部结果，而且逐层检查错误会淹没主要逻辑。异常提供了另一条控制流：在发现处 `throw`，沿调用栈传播，在能够处理的位置 `catch`。

```cpp
#include <fstream>
#include <iterator>
#include <stdexcept>
#include <string>

std::string load_text(const std::string& path) {
    std::ifstream input{path};
    if (!input)
        throw std::runtime_error{"cannot open file: " + path};

    return {std::istreambuf_iterator<char>{input},
            std::istreambuf_iterator<char>{}};
}
```

异常并不等于崩溃。只有异常一路传播却没有匹配的处理器时，程序才会调用 `std::terminate`。应用程序可以在边界统一处理：

```cpp
int main() {
    try {
        run_application();
        return 0;
    } catch (const std::exception& error) {
        std::cerr << "grades: " << error.what() << '\n';
        return 1;
    }
}
```

不要 `catch (...)` 后什么也不做。吞掉错误会让程序带着不清楚的状态继续运行。若当前层不能真正处理，可以补充上下文后继续抛出，或者干脆不捕获。

## 返回值、`expected` 与异常怎样选择

没有一种机制适合所有项目，可以从下面的默认判断开始：

| 情况                             | 常见选择                         |
| -------------------------------- | -------------------------------- |
| 没有结果是正常分支，不需原因     | `std::optional<T>`               |
| 失败常见，调用者预计立即分支处理 | `std::expected<T, E>` 或结果类型 |
| 失败不能在当前层处理             | 异常                             |
| 只有程序缺陷才会发生             | 断言、契约检查、修复代码         |
| 进程入口需要映射给操作系统       | `main` 的退出码                  |

错误码也可以工作，例如返回一个 `enum class` 并通过输出参数交付结果。但必须检查的结果类型通常能更直接地把成功值和错误绑定在一起。不要返回 `bool` 却不给它稳定含义，也不要用 `-1` 同时表达正常数据和失败。

选择还受项目边界影响：

- 跨 C 接口或某些 ABI 边界通常不能让 C++ 异常直接穿过；
- 实时、嵌入式或禁用异常的项目会采用明确的结果类型；
- 既有代码库通常已有统一约定，保持一致往往比局部发明新体系更重要。

## 在能作决定的层处理

假设成绩程序分为输入层、领域层和界面层：

```text
用户界面 -> 读取一行文本 -> 解析分数 -> 建立 Score
   ↑             错误上下文逐层补充，但不重复处理
```

`Score` 只负责保证 `0` 到 `100` 的不变式，不知道文本从终端还是文件而来。解析层知道“不是整数”和“数值越界”的区别，但不必决定提示颜色。最外层知道当前交互方式，适合把错误转成用户能理解的消息，并决定重试还是退出。

错误处理最常见的问题之一，是每一层都打印一次：

```text
parse_score: out of range
read_student: failed
import_file: failed
application: import failed
```

这样既重复又缺少结构。更好的做法是让底层返回或抛出错误，沿途只在确实增加有用上下文时包装，最终在边界记录或展示一次。

## 日志不是用户提示

面向用户的错误提示要说明用户能做什么：

```text
第 8 行成绩为 130，应为 0 到 100 之间的整数。
```

日志则服务于开发和运维，可能包含时间、源文件、请求编号、底层错误码和调用上下文：

```text
2026-09-30T20:14:03Z WARN import row=8 error=score_out_of_range value=130
```

二者可能源于同一个结构化错误，但受众和内容不同。库通常不应直接往 `std::cerr` 打印；否则图形界面、测试和服务器都难以控制输出。让错误返回到应用边界，由应用决定是否展示、记录或重试。

同时避免把密码、令牌和完整个人信息写进日志。错误处理不能成为数据泄露通道。

## 异常安全依赖 RAII

异常会跳过当前控制流，逐层销毁已经完成构造的局部对象。正因如此，资源应交给对象管理：

```cpp
void save_report(const std::filesystem::path& path) {
    std::ofstream output{path};
    if (!output)
        throw std::runtime_error{"cannot create report"};

    std::vector<Student> students = load_students();
    write_report(output, students); // 即使抛出，文件和 vector 仍会析构
}
```

如果这里手工 `new`、手工加锁或手工打开 C 风格文件，异常路径很容易漏掉清理。`std::vector`、文件流、智能指针和锁守卫会在栈展开时自动释放资源。

常见的异常安全保证有三档：

- **基本保证**：失败后没有资源泄漏，对象仍然有效，但状态可能已经改变；
- **强保证**：失败后操作像没有发生过，对象保持原状态；
- **不抛出保证**：操作承诺不会让异常逃出，通常以 `noexcept` 表达。

一种容易获得强保证的写法是先在临时对象中完成可能失败的工作，成功后再提交状态：

```cpp
void Roster::replace_from(std::istream& input) {
    auto replacement = read_all_students(input); // 可能抛出
    students_ = std::move(replacement);           // 成功后提交
}
```

`noexcept` 是契约，不是优化装饰。如果标为 `noexcept` 的函数仍让异常逃出，程序会终止。只有确实能保证时才写。

析构函数尤其不应让异常逃出，因为它可能正在另一个异常的栈展开过程中运行。需要报告的关闭或提交错误，应通过显式操作在正常路径处理；析构仍负责兜底释放资源。

## 一条实用的设计顺序

为一个可能失败的函数设计接口时，可以依次询问：

1. 这是外部世界中预期会发生的失败，还是程序缺陷？
2. 调用者是否需要区分失败原因？
3. 当前调用者能否恢复，还是只能把问题交给更高层？
4. 失败时对象仍满足什么不变式？是否泄漏资源？
5. 错误最终在哪个边界被展示或记录？

先回答这些问题，再决定写 `optional`、结果类型、异常还是断言。语法只是设计的最后一步。

## 小结

- 断言检查程序员必须维护的内部假设，不能代替外部输入校验
- `optional` 表达正常缺失，`expected` 或结果类型表达带原因的预期失败
- 异常适合把当前层无法处理的失败传播到合适边界
- 错误应在能够作决定的层处理，底层库不应擅自打印或退出进程
- 用户提示和日志受众不同，应由结构化错误派生而不是混在一起
- RAII 让正常返回和异常路径使用同一套资源清理机制
- 设计修改操作时，应明确提供基本、强或不抛出保证中的哪一种
