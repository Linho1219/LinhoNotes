# 3.1 初探多文件项目

在上一章结尾，我们已经把成绩程序写得像一个现代 C++ 程序了。不过所有代码仍挤在同一个文件中。程序只有两百行时这没什么问题，但当继续加入更多功能、统计、命令行选项和测试时，代码规模逐渐扩大，这种做法是不可持续的。

根据 Open Hub 的统计，截至 2026 年 10 月 26 日，排除空行与注释行，Chromium 共有 20,838,093 行 C++ 代码！除了 C++ 外，Chromium 中还有 Rust、Java、JS 等其他语言，总行数在四千万以上。你也可以随时 [在 Open Hub 上查询最新的数字](https://openhub.net/p/chrome/analyses/latest/languages_summary)。

当然，如此大的代码库是极端情况，我们的项目无法达到这样的规模，但本质需求是一致的：都需要合理地将组织代码组织到不同文件中。这会迫使我们回答几个工程问题：如何对外设计接口，是否隐藏实现细节？如何合理命名、方便调用？修改一处代码后，哪些部分必须重新编译？

## 从源码到程序

粗略地说，构建一个 C++ 多文件程序要经过两步：

1. 每个源文件分别经过预处理和编译，产生**目标文件**（object file）；
2. 链接器把目标文件和所需的库组合起来，产生可执行文件。

一个源文件以及它递归包含的所有头文件，在预处理后构成一个**翻译单元**（translation unit）。例如：

$$
\left.\begin{aligned}
\texttt{src/main.cpp} + \text{头文件} &\to \texttt{main.o} \\
\texttt{src/student.cpp} + \text{头文件} &\to \texttt{student.o}
\end{aligned}\right\}\to
\texttt{grades.exe}
$$

## 分离声明与定义

我们已经知道，函数可以先声明后定义。**声明**告诉编译器一个名字及其类型存在，**定义**则真正提供实体，或者为它分配存储。

```cpp
int square(int value);              // 声明
int square(int value) {             // 定义
    return value * value;
}
```

当 `main.cpp` 调用只有声明的 `square` 时，编译器已经知道怎样检查参数和返回值。这样，函数体可以放在另一个翻译单元，链接器稍后再把调用和定义接起来。所以，类的定义通常放在头文件里，因为编译器需要知道类的成员和布局，才能创建对象、访问成员并检查调用。而成员函数的函数体则可以放进源文件。

下面是一个实际例子：

```cpp [include/grades/student.hpp]
#pragma once

#include <optional>

namespace grades {

class Score {
  public:
    [[nodiscard]] static std::optional<Score> from(int value);
    [[nodiscard]] int value() const noexcept;
    [[nodiscard]] bool passed(int threshold = 60) const noexcept;

  private:
    explicit Score(int value);
    int value_;
};

} // namespace grades
```

```cpp [src/student.cpp]
#include "grades/student.hpp"

namespace grades {

std::optional<Score> Score::from(int value) {
    if (value < 0 || value > 100)
        return std::nullopt;
    return Score{value};
}

int Score::value() const noexcept { return value_; }

bool Score::passed(int threshold) const noexcept {
    return value_ >= threshold;
}

Score::Score(int value) : value_{value} {}

} // namespace grades
```

成员函数定义中的 `Score::` 表示这个函数属于 `Score`。在这个例子里，`include/grades/student.hpp` 中声明的 `Score::from`、`Score::value`、`Score::passed`、`Score::Score` 这些成员函数在 `student.cpp` 中一一定义。

这样还带来另一个好处：修改函数体时，一般只需重新编译对应源文件即可。而修改头文件则会影响所有包含它的翻译单元。

## 头文件的注意事项

头文件可能被很多源文件包含，也可能通过其他头文件间接包含。它应当满足两个基本要求。

### 防止重复处理

防止同一个翻译单元重复处理其中的定义。比较传统的写法是 include guard：

```cpp
#ifndef GRADES_STUDENT_HPP
#define GRADES_STUDENT_HPP

// 头文件内容

#endif
```

也可以使用 `#pragma once`。

```cpp
#pragma once

// 头文件内容
```

`#pragma once` 不是 C++ 标准规定的指令，但主流编译器广泛支持，在常见工具链中使用很普遍。二者选择一种即可，不必同时写。

### 避免依赖包含顺序

头文件应直接包含自己所依赖的声明，不要碰巧依赖包含顺序：

```cpp
// 错误：使用 std::string，却希望调用者事先包含 <string>
struct Student {
    std::string name;
};
```

```cpp
// 正确：自己带上 #include <string>
#pragma once
#include <string>

struct Student {
    std::string name;
};
```

一个简单的检查方法是：在对应源文件中首先包含自己的头文件。如果头文件漏掉依赖，编译器一般会马上指出。

## 命名空间

命名空间，顾名思义，用于给名字建立边界。一般来说，项目公开接口应有自己的顶层命名空间。

```cpp
namespace grades {

struct Student {
    int id{};
    std::string name;
    Score score;
};

} // namespace grades
```

调用处写作 `grades::Student`。这样，如果另一个命名空间 `foo` 也定义了 `Student`，就写作 `foo::Student`，避免了冲突。

在很小的局部作用域可以使用 `using grades::Student;`，这样在这个作用域中 `Student` 就直接对应 `grades::Student`。**在头文件中不应该这样做**！这样会把名字注入**每个包含者**，大大增加命名冲突的风险。

如果使用 `using namespace grades;`，会把命名空间 `grades` 中的所有名字都注入到当前作用域。通常情况下也不应该这么做。一些算法竞赛教材或课程中会使用 `using namespace std;`，将 `std` 标准库命名空间的所有名字都拿出来，**这在工程上是非常不推荐的**。

## 多文件程序的编译与链接

### 手动编译与链接

还是考虑一开始提到过的成绩程序。我们可以这样拆分它：

```
grades/
├── include/
│   └── grades/
│       ├── student.hpp
│       └── io.hpp
└── src/
    ├── student.cpp
    ├── io.cpp
    └── main.cpp
```

`include/grades` 中放置允许其他目标包含的公开头文件，实现则放置在 `src` 里，包含时使用 `#include "grades/student.hpp"`。一般地，搜索路径应由构建命令统一提供，源码不依赖自己在磁盘上的相对位置（这和一些其他语言的常见开发习惯不同），所以不要写 `../include/...`。

在 MSYS2 UCRT64 终端中，可以手工构建它：

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -Iinclude -c src/student.cpp -o student.o
g++ -std=c++20 -Wall -Wextra -Wpedantic -Iinclude -c src/io.cpp -o io.o
g++ -std=c++20 -Wall -Wextra -Wpedantic -Iinclude -c src/main.cpp -o main.o
g++ main.o student.o io.o -o grades.exe
```

`-Iinclude` 用于增加头文件搜索路径，`-c` 表示只编译、不链接。最后一条命令才执行链接。

这些命令看着非常冗杂，而且手动执行它们也很容易出错。随着项目增长、文件变多，这种做法明显不可持续。因此，我们会在 [下一节](./3.2-使用CMake管理项目) 介绍如何将这些关系交给 CMake 自动化管理。

### 常见的编译与链接错误

看到错误时，应该先判断它来自编译器还是链接器，这样可以缩小排查范围。编译错误发生在单个单元内，而链接错误发生在组合目标文件的过程中。

如果调用函数时编译器根本没见过声明，会在编译阶段失败：

```text
error: 'read_student' was not declared in this scope
```

如果声明存在，但所有参与链接的目标文件中都没有相应定义，则通常在链接阶段失败：

```text
undefined reference to `grades::read_student(std::istream&)'
```

如果同一个普通函数被定义了多次，也会在链接阶段失败：

```text
multiple definition of `grades::passed(...)'
```

链接错误中要注意完整的参数类型。声明和定义只差一个 `const`、命名空间或引用，都会使之成为两个不同的符号。

### 单一定义规则 ODR

C++ 的**单一定义规则**（One Definition Rule，ODR）约束实体可以出现多少份定义。

- 普通的非 `inline` 函数和具有外部链接的变量，在整个程序中只能有一份定义；
- 类、模板以及 `inline` 函数可以在多个翻译单元中出现定义，但这些定义必须一致；
- 只在一个 `.cpp` 中使用的名字，可以放进匿名命名空间，使它具有翻译单元内部的链接。

因此，不能把普通函数定义直接写进会被多个源文件包含的头文件：

```cpp
// 错误：每个包含者都可能产生一份外部定义
int passing_score() { return 60; }
```

小而适合放在头文件的函数可以明确写成 `inline`，类定义内部定义的成员函数也隐式为 `inline`：

```cpp
inline int passing_score() { return 60; }
```

这样即可允许相同定义出现在多个翻译单元。

**特别地，模板的定义通常也必须放在头文件中**。这是因为编译器实例化模板时需要看到完整定义，否则无法判断操作是否合法。

```cpp [include/grades/io.hpp]
std::optional<Student> read_student(std::istream &input);
```


```cpp [src/io.cpp]
#pragma once

#include <optional>
#include <string>

namespace grades {

class Score {
  public:
    [[nodiscard]] static std::optional<Score> from(int value);
    [[nodiscard]] int value() const noexcept;
    [[nodiscard]] bool passed(int threshold = 60) const noexcept;

  private:
    explicit Score(int value);
    int value_;

    int id{};
```

```cpp [src/main.cpp]
#include "grades/io.hpp"
#include "grades/student.hpp"
#include <cstddef>
#include <iostream>
#include <optional>
#include <ranges>
#include <string>
#include <utility>
#include <vector>

int main() {
    int count{};
    std::cout << "Number of students: ";
    if (!(std::cin >> count) || count < 0) {
        std::cerr << "Invalid student count\n";
        return 1;
    }

    std::vector<grades::Student> students;
    students.reserve(static_cast<std::size_t>(count));

    std::cout << "Enter id, name and score for each student:\n";
    for (int index{}; index < count; ++index) {
        auto student = grades::read_student(std::cin);
        if (!student) {
            std::cerr << "Invalid student data\n";
            return 1;
        }
        students.push_back(std::move(*student));
    }

    auto failed_students =
        students | std::views::filter([](const grades::Student &student) {
            return !student.score.passed();
        });

    std::cout << "Students who failed:\n";
    for (const grades::Student &student : failed_students) {
        grades::write_student(std::cout, student);
    }
}
```

:::

- 每个源文件及其包含内容构成一个翻译单元，翻译单元先分别编译，再参与链接
- 头文件主要描述接口，源文件主要承载实现
- 头文件应防止重复包含，并直接包含自己的依赖
- 命名空间组织 C++ 名字，目录组织磁盘文件，二者解决不同问题
- 编译错误发生在单个翻译单元内，链接错误发生在组合目标文件时
- ODR 约束定义数量与一致性
