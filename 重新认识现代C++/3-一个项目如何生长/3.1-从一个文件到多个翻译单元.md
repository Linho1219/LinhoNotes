# 3.1 从一个文件到多个翻译单元

在上一章结尾，我们已经把成绩程序写得像一个现代 C++ 程序了。不过所有代码仍挤在同一个文件中。程序只有两百行时这很方便；当它继续加入文件读写、统计、命令行选项和测试时，任何修改都要面对整份源码，任何复用也只能靠复制粘贴。

拆分文件并不只是整理代码。它会迫使我们回答几个工程问题：什么是对外接口，什么是实现细节；哪些名字属于同一个模块；修改一处代码后，哪些部分必须重新编译。

## 从源码到程序

C++ 不会把整个项目一次性当作一份文本处理。粗略地说，构建一个多文件程序要经过两步：

1. 每个源文件分别经过预处理和编译，产生**目标文件**（object file）；
2. 链接器把目标文件和所需的库组合起来，产生可执行文件。

一个源文件以及它递归包含的所有头文件，在预处理后构成一个**翻译单元**（translation unit）。例如：

```text
src/main.cpp  + 它包含的头文件  -> main.o
src/student.cpp + 它包含的头文件 -> student.o
main.o + student.o                -> grades.exe
```

`#include` 本质上很接近文本包含。头文件不会独立成为翻译单元，也不会因为被包含过一次就“自动参与链接”。真正分别编译的是 `.cpp` 源文件。

## 声明与定义

**声明**告诉编译器一个名字及其类型存在；**定义**则真正提供实体，或者为它分配存储。函数可以先声明后定义：

```cpp
int square(int value);              // 声明
int square(int value) {             // 定义
    return value * value;
}
```

当 `main.cpp` 调用只有声明的 `square` 时，编译器已经知道怎样检查参数和返回值。函数体可以放在另一个翻译单元，链接器稍后再把调用和定义接起来。

类的定义通常放在头文件里，因为编译器需要知道类的成员和布局，才能创建对象、访问成员并检查调用。成员函数的函数体则可以放进源文件：

```cpp
// include/grades/student.hpp
#pragma once

#include <optional>

namespace grades {

class Score {
  public:
    [[nodiscard]] static std::optional<Score> from(int value);
    [[nodiscard]] int value() const noexcept;
    [[nodiscard]] bool passed(int threshold = 60) const noexcept;

  private:
    explicit Score(int value);
    int value_;
};

} // namespace grades
```

```cpp
// src/student.cpp
#include "grades/student.hpp"

namespace grades {

std::optional<Score> Score::from(int value) {
    if (value < 0 || value > 100)
        return std::nullopt;
    return Score{value};
}

Score::Score(int value) : value_{value} {}

int Score::value() const noexcept { return value_; }

bool Score::passed(int threshold) const noexcept {
    return value_ >= threshold;
}

} // namespace grades
```

成员函数定义中的 `Score::` 表示这个函数属于 `Score`。头文件描述可供其他代码使用的接口，源文件保存实现。修改函数体时，通常只需重新编译对应源文件；修改头文件则会影响所有包含它的翻译单元。

## 头文件应当能独立使用

头文件可能被很多源文件包含，也可能通过其他头文件间接包含。它应当满足两个基本要求。

第一，防止同一个翻译单元重复处理其中的定义。可以使用传统的 include guard：

```cpp
#ifndef GRADES_STUDENT_HPP
#define GRADES_STUDENT_HPP

// 头文件内容

#endif
```

也可以使用被主流编译器广泛支持的 `#pragma once`。它不是 C++ 标准规定的指令，但在常见工具链中使用很普遍。二者选择一种即可，不必同时写。

第二，头文件应直接包含自己所依赖的声明，不要碰巧依赖包含顺序：

```cpp
// 错误：使用 std::string，却希望调用者事先包含 <string>
struct Student {
    std::string name;
};
```

```cpp
#pragma once
#include <string>

struct Student {
    std::string name;
};
```

一个简单的检查方法是：在对应源文件中首先包含自己的头文件。如果头文件漏掉依赖，编译器更容易立刻指出。

只需要声明而不需要完整定义时，可以使用前置声明，标准库也提供 `<iosfwd>` 来声明流类型：

```cpp
#pragma once

#include "grades/student.hpp"

#include <iosfwd>
#include <optional>

namespace grades {

std::optional<Student> read_student(std::istream& input);

} // namespace grades
```

但不要为了少包含几个头文件而到处手写前置声明，尤其不能自行前置声明标准库类型。先保证接口正确、依赖清楚，再处理确实造成构建瓶颈的问题。

## 用命名空间组织名字

目录只能组织文件，不能阻止两个库都定义 `Student`。命名空间给 C++ 名字建立边界：

```cpp
namespace grades {

struct Student {
    int id{};
    std::string name;
    Score score;
};

} // namespace grades
```

调用处写作 `grades::Student`。在很小的局部作用域可以使用 `using grades::Student;`，但不应在头文件中写 `using namespace grades;`，更不应在头文件中写 `using namespace std;`。头文件中的 `using namespace` 会把名字注入每个包含者，容易产生冲突。

命名空间不必机械地映射每一级目录，但项目公开接口通常应有自己的顶层命名空间。

## 拆分成绩程序

可以先得到下面的目录：

```text
grades/
├── include/
│   └── grades/
│       ├── io.hpp
│       └── student.hpp
└── src/
    ├── io.cpp
    ├── main.cpp
    └── student.cpp
```

`include/grades` 中放允许其他目标包含的公开头文件，`src` 中放实现。包含时使用 `#include "grades/student.hpp"`，而不是写 `../include/...`。搜索路径应由构建命令统一提供，源码不应知道自己在磁盘上的相对位置。

在 MSYS2 UCRT64 终端中，可以手工构建它：

```sh
g++ -std=c++20 -Wall -Wextra -Wpedantic -Iinclude -c src/student.cpp -o student.o
g++ -std=c++20 -Wall -Wextra -Wpedantic -Iinclude -c src/io.cpp -o io.o
g++ -std=c++20 -Wall -Wextra -Wpedantic -Iinclude -c src/main.cpp -o main.o
g++ main.o student.o io.o -o grades.exe
```

`-Iinclude` 增加头文件搜索路径，`-c` 表示只编译、不链接。最后一条命令才执行链接。

这些命令帮助我们看清过程，却不适合作为长期构建方式。源文件越来越多后，手写命令很容易漏文件、漏选项或重复编译，下一节会把这些关系交给 CMake 管理。

## 看懂编译错误与链接错误

如果调用函数时编译器根本没见过声明，会在编译阶段失败：

```text
error: 'read_student' was not declared in this scope
```

如果声明存在，但所有参与链接的目标文件中都没有相应定义，则通常在链接阶段失败：

```text
undefined reference to `grades::read_student(std::istream&)'
```

另一个常见链接错误是同一个普通函数被定义了多次：

```text
multiple definition of `grades::passed(...)'
```

看到错误时先判断它来自编译器还是链接器，排查范围会小很多。链接错误中完整的参数类型也很重要：声明和定义只差一个 `const`、命名空间或引用，也会成为两个不同符号。

## ODR：定义不能各说各话

C++ 的**单一定义规则**（One Definition Rule，ODR）约束实体可以出现多少份定义。对初学阶段，可以先记住：

- 普通的非 `inline` 函数和具有外部链接的变量，在整个程序中通常只能有一份定义；
- 类、模板以及 `inline` 函数可以在多个翻译单元中出现定义，但这些定义必须一致；
- 只在一个 `.cpp` 中使用的名字，可以放进匿名命名空间，使它具有翻译单元内部的链接。

因此，不要把普通函数定义直接写进会被多个源文件包含的头文件：

```cpp
// 错误：每个包含者都可能产生一份外部定义
int passing_score() { return 60; }
```

小而适合放在头文件的函数可以明确写成 `inline`，类定义内部定义的成员函数也隐式为 `inline`：

```cpp
inline int passing_score() { return 60; }
```

这里 `inline` 最关键的工程含义是允许相同定义出现在多个翻译单元，并不保证编译器一定把函数调用展开。模板的定义通常也必须放在头文件中，因为编译器实例化模板时需要看到完整定义。

## 库是什么

库可以先理解为经过组织、供其他目标复用的编译产物。

**静态库**在链接时把所需代码纳入最终程序。发布时通常少一个运行时文件依赖，但各个程序会各自带上一份所需代码。

**动态库**在程序运行时装载，例如 Windows 上常见的 `.dll`。多个程序可以共享它，也能独立替换库文件，但需要处理部署、搜索路径、版本兼容和导出符号等问题。

头文件既不是静态库也不是动态库，它只是向编译器提供接口。库的二进制中则包含实现。现阶段无需手写 `ar` 或 DLL 导出宏；CMake 可以用同一套目标模型生成静态库或动态库。

## 小结

- 每个源文件及其包含内容构成一个翻译单元，翻译单元先分别编译，再参与链接
- 头文件主要描述接口，源文件主要承载实现
- 头文件应防止重复包含，并直接包含自己的依赖
- 命名空间组织 C++ 名字，目录组织磁盘文件，二者解决不同问题
- 编译错误发生在单个翻译单元内，链接错误发生在组合目标文件时
- ODR 约束定义数量与一致性；`inline` 不等于“强制展开调用”
- 库是可复用的构建目标，不是随手复制的一组源文件
