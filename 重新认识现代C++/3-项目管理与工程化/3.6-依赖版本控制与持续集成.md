# 3.6 依赖、版本控制与持续集成

到目前为止，项目已经能构建、处理错误、运行测试，也能接受各种工具检查。但“在我的电脑上可以运行”还不是一个可协作的项目。其他人需要知道怎样取得依赖、怎样复现构建；每次修改也需要留下原因，并在干净环境中重新验证。

这一节把三件看似独立的事连接起来：

```text
依赖声明决定需要什么
版本控制记录项目是什么
持续集成验证从记录的内容能否重新得到正确结果
```

## 不要随手复制第三方源码

需要格式化、JSON、网络或测试能力时，把网上找到的 `.hpp`、`.cpp` 直接复制进 `src` 看起来最快，却会留下很多问题：

- 不知道代码来自哪个版本，是否被本地修改；
- 许可证和版权声明容易在复制时丢失；
- 安全修复和兼容更新难以跟踪；
- 头文件路径、编译选项和传递依赖只能手工维护；
- 仓库里混入大量不属于项目自身的代码。

少量、稳定且项目明确承担维护责任的 vendoring 并非绝对错误，但它应当是有记录的决定。通常更好的默认方式是：用包管理器声明直接依赖，用构建系统消费包提供的目标。

## `find_package` 查找已经可用的包

CMake 的 `find_package` 查找包提供的配置或查找模块。例如使用 Catch2 测试框架：

```cmake
find_package(Catch2 3 CONFIG REQUIRED)

add_executable(grades_tests
    score_test.cpp
    statistics_test.cpp
)
target_link_libraries(grades_tests PRIVATE
    grades_core
    Catch2::Catch2WithMain
)

include(Catch)
catch_discover_tests(grades_tests)
```

`Catch2::Catch2WithMain` 是包导出的 CMake 目标。链接它时，所需头文件目录、编译定义和库文件会作为使用要求传播，不必手工写出安装路径。

`find_package` 本身通常**不负责下载或安装**。它回答的是“某个包在哪里，以及怎样使用”。包从哪里来，可以由系统包管理器、vcpkg、Conan、手工安装或上级项目提供。

不要退回到手工设置全局 `include_directories` 和 `link_directories`。现代 CMake 包应尽量提供带命名空间的导入目标，调用者链接目标即可。

## 用 vcpkg manifest 声明依赖

vcpkg 和 Conan 都是常见的 C/C++ 包管理器。它们的模型和擅长场景有所不同，本节选择 vcpkg 的 manifest 模式演示一条完整路径，并不意味着所有项目都必须作同样选择。

在项目根目录创建 `vcpkg.json`：

```json
{
  "name": "grades",
  "version-string": "0.1.0",
  "dependencies": ["catch2"]
}
```

manifest 只声明项目的直接依赖。vcpkg 会解析 Catch2 需要的传递依赖，并把当前项目的包安装到独立的 `vcpkg_installed` 目录。这个目录是可恢复的构建产物，不应提交到 Git。

安装 vcpkg 的一种方式是把官方仓库克隆到固定位置并运行 bootstrap。项目需要记录团队正在使用的 vcpkg 提交；可以用文档、CI 中固定的提交号，或 Git submodule 保存这个关系。不能只写“永远使用最新版”，否则半年后同一 manifest 可能解析到不同的 port 内容。

在前文的 MSYS2 UCRT64 环境中使用 MinGW 时，还需要明确目标和宿主 triplet。例如在终端中：

```sh
export VCPKG_ROOT=/d/tools/vcpkg
export VCPKG_DEFAULT_TRIPLET=x64-mingw-dynamic
export VCPKG_DEFAULT_HOST_TRIPLET=x64-mingw-dynamic
```

然后让 CMake 在第一次 `project()` 之前使用 vcpkg 的 toolchain 文件。可以增加一个本地 preset：

```json
{
  "name": "debug-vcpkg",
  "inherits": "debug",
  "binaryDir": "${sourceDir}/build/debug-vcpkg",
  "toolchainFile": "$env{VCPKG_ROOT}/scripts/buildsystems/vcpkg.cmake",
  "cacheVariables": {
    "VCPKG_TARGET_TRIPLET": "x64-mingw-dynamic",
    "VCPKG_HOST_TRIPLET": "x64-mingw-dynamic"
  }
}
```

配置时，vcpkg 会根据 `vcpkg.json` 恢复依赖：

```sh
cmake --preset debug-vcpkg
cmake --build build/debug-vcpkg
ctest --test-dir build/debug-vcpkg --output-on-failure
```

若使用 MSVC，则通常选择 `x64-windows` 等对应 triplet，不能把一套编译器构建的 C++ 库随意交给另一套 ABI 使用。triplet 不只是“64 位”标签，它还参与确定平台、链接方式和工具链。

vcpkg 的 toolchain 路径属于开发环境，不应硬编码为某位开发者的 `D:\\tools\\...`。用环境变量、用户 preset 或命令行提供机器相关位置，共享 preset 只保存团队认可的逻辑配置。

## 可复现不等于提交所有产物

一个可复现项目通常提交：

- 自己的源码、头文件和测试；
- `CMakeLists.txt` 与共享 presets；
- 依赖 manifest 和用于解析依赖的版本依据；
- 格式化、静态分析和 CI 配置；
- README、许可证和必要文档。

通常不提交：

- `build/`、目标文件、可执行文件；
- `vcpkg_installed/` 等可恢复依赖目录；
- 编辑器缓存和操作系统临时文件；
- 包含令牌、密码和本地绝对路径的配置。

`.gitignore` 可以先包含：

```text
/build/
/vcpkg_installed/
/CMakeUserPresets.json
```

锁定依赖来源和版本，与提交编译产物是两回事。前者让工具重新获得同样的输入，后者把特定机器生成的结果塞进仓库。

## 用 Git 记录可以解释的变化

Git 的提交不是定时存档，而是项目历史中的一个有意义变化。一份容易评审的提交通常具有这些特点：

- 只解决一个相对完整的问题；
- 提交前能够构建并通过相关测试；
- 不混入无关格式化、临时输出和个人配置；
- 提交消息说明改变了什么，必要时解释为什么。

例如：

```text
Reject scores outside the valid range

Keep Score's invariant at its construction boundary so callers cannot
accidentally store invalid values.
```

第一行简短概括结果，正文补充无法从 diff 直接看出的动机。不要只写 `update`、`fix` 或 `changes`。

一种简单协作流程是：

1. 从最新主分支创建短生命周期分支；
2. 分几次提交完成一个聚焦变化；
3. 推送分支并创建 pull request；
4. 由自动检查和其他开发者评审；
5. 根据反馈修改，检查通过后合并。

分支不是长期分叉的副本。越早、越频繁地与主线同步，冲突越容易理解。解决冲突后必须重新构建和测试，因为“两边文本都保留了”不等于组合后的语义正确。

代码评审也不只是找语法错误。评审者更适合检查接口是否清楚、错误路径是否完整、测试是否真的覆盖新行为、依赖与安全影响是否合理。格式问题尽量交给自动化工具。

## 持续集成重新验证项目

持续集成（Continuous Integration，CI）在代码推送或 pull request 时，用一台干净机器自动执行构建和检查。它主要回答：

> 仅凭仓库中记录的内容和声明的外部依赖，项目现在还能成功构建并通过测试吗？

下面是一份简化的 GitHub Actions 工作流，保存为 `.github/workflows/ci.yml`。它假设 vcpkg 以 Git submodule 位于项目的 `vcpkg` 目录，并锁定在仓库记录的提交：

```yaml
name: CI

on:
  push:
  pull_request:

permissions:
  contents: read

jobs:
  build-and-test:
    runs-on: ubuntu-latest

    env:
      VCPKG_ROOT: ${{ github.workspace }}/vcpkg

    steps:
      - name: Check out sources
        uses: actions/checkout@v7
        with:
          submodules: true

      - name: Bootstrap vcpkg
        run: ./vcpkg/bootstrap-vcpkg.sh -disableMetrics

      - name: Configure
        run: >-
          cmake -S . -B build -G Ninja
          -DCMAKE_BUILD_TYPE=Debug
          -DCMAKE_TOOLCHAIN_FILE="$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake"

      - name: Build
        run: cmake --build build

      - name: Test
        run: ctest --test-dir build --output-on-failure
```

Action 的主版本会随时间更新，实际项目应参考官方发布说明，并按安全策略固定主版本或完整提交 SHA。本例中的版本表示写作时的主版本，不是永久不变的知识。

CI 不需要照搬开发者的整台电脑。它应复用同一套 CMake 目标和测试命令，同时显式安装或恢复缺少的工具与依赖。若 CI 只能依赖某人机器上预先装好的库，就失去了可复现价值。

项目进一步发展后，可以增加构建矩阵：

- GCC、Clang 和 MSVC；
- Debug 与 Release；
- Linux、Windows 和 macOS；
- sanitizer、`clang-tidy` 和格式检查。

矩阵不是越大越好。优先覆盖真正支持的平台和编译器，避免大量从不处理的红灯。快速、稳定的检查应作为合并门槛，耗时任务可以分层执行。

CI 中的第三方 action 和构建脚本都会执行代码。工作流权限应遵循最小权限原则，外部贡献触发的工作流不能随意获得发布密钥。依赖和 action 也需要像生产代码一样审查、更新和固定版本。

## README 是项目入口

一个第一次看到仓库的人，不应通过猜测才能构建。README 至少应回答：

- 这个项目解决什么问题，目前处于什么状态；
- 支持哪些平台、编译器和 C++ 标准；
- 需要安装哪些工具；
- 如何配置、构建、运行和测试；
- 第三方依赖怎样恢复；
- 目录大致如何组织；
- 怎样参与贡献，到哪里报告问题；
- 使用什么许可证。

命令应当可以复制，并与 CI 实际执行的步骤尽量一致。README 不是一次写完的宣传页，而是接口的一部分：构建方式变化时也要更新它。

## 项目至此长成了什么

这一篇开始时，成绩程序只是一个源文件。现在它大致具有这样的结构：

```text
grades/
├── .github/
│   └── workflows/
│       └── ci.yml
├── include/
│   └── grades/
│       ├── io.hpp
│       ├── statistics.hpp
│       └── student.hpp
├── src/
│   ├── io.cpp
│   ├── main.cpp
│   ├── statistics.cpp
│   └── student.cpp
├── tests/
│   ├── CMakeLists.txt
│   ├── score_test.cpp
│   └── statistics_test.cpp
├── .clang-format
├── .clang-tidy
├── .gitignore
├── CMakeLists.txt
├── CMakePresets.json
├── README.md
├── vcpkg/              # 可选：固定到某一提交的 Git submodule
└── vcpkg.json
```

目录树本身不是目标。真正的变化是：接口和实现有了边界，依赖关系可以由机器理解，错误可以沿清晰路径传播，行为可以重复验证，任何人都能从版本记录中重建项目。

## 小结

- 第三方依赖应有来源、版本和许可证记录，不要无来由地复制源码
- `find_package` 负责找到和导入包，包管理器负责取得依赖
- vcpkg manifest 声明直接依赖，toolchain 文件把依赖接入 CMake
- 可复现依赖版本依据，不意味着把构建目录和二进制提交进仓库
- Git 提交应聚焦、可构建、可解释，代码评审关注行为与设计
- CI 在干净环境中重复配置、构建和测试，并应遵循最小权限原则
- README 是项目面向新使用者和贡献者的入口，应保存可复制的真实步骤
