# 3.4 测试一个 C++ 程序

“我刚才运行过，结果是对的”只能说明那一次、那组输入没有暴露问题。项目继续生长后，我们需要一组可以重复执行的检查：修改实现后运行它们，快速确认原有行为是否仍然成立。

自动化测试也是代码。它调用被测接口、安排输入、检查输出，并用进程退出状态告诉构建工具测试是否通过。

## 单元测试测试什么

单元测试关注一个较小、边界清楚的行为单元。这个“单元”不一定等于一个函数，也不要求把每个私有成员都隔离测试。更有价值的问题是：

- 给定输入后，公开接口产生什么可观察结果？
- 类的不变式能否一直成立？
- 边界值和失败路径是否符合契约？

测试不应复制实现过程。如果生产代码和测试都照抄同一个错误算法，两边会一起通过。测试应从接口契约出发。

## 从纯函数开始

纯函数不读取隐藏状态，也不修改外部对象。同样的输入会产生同样的输出，因此最容易测试：

```cpp
double average(std::span<const int> values);
```

我们暂时不用第三方测试框架，先写一个极小的测试程序，看清其本质：

```cpp
// tests/statistics_test.cpp
#include "grades/statistics.hpp"

#include <cmath>
#include <iostream>
#include <vector>

namespace {

int failures{};

void expect_near(double actual, double expected, double tolerance,
                 const char* description) {
    if (std::abs(actual - expected) <= tolerance)
        return;

    std::cerr << "FAILED: " << description << "\n"
              << "  expected: " << expected << "\n"
              << "  actual:   " << actual << '\n';
    ++failures;
}

} // namespace

int main() {
    expect_near(grades::average(std::vector{60, 70, 80}), 70.0, 0.001,
                "average of three scores");
    expect_near(grades::average(std::vector{100}), 100.0, 0.001,
                "average of one score");

    return failures == 0 ? 0 : 1;
}
```

测试失败时应输出足够信息，成功时返回 `0`，失败时返回非零。CTest 不理解测试程序内部的 C++ 表达式，它只负责运行程序、观察退出状态并收集输出。

浮点数通常不应直接用 `==` 比较计算结果，因此示例使用容差。容差大小应来自问题的精度要求，而不是随意添加一个“很小的数”。

## 测试类的不变式

`Score` 的核心契约是值始终位于 `0` 到 `100`。测试应覆盖有效区域和边界外：

```cpp
#include "grades/student.hpp"

#include <iostream>

namespace {

int failures{};

void expect(bool condition, const char* description) {
    if (condition)
        return;
    std::cerr << "FAILED: " << description << '\n';
    ++failures;
}

} // namespace

int main() {
    const auto zero = grades::Score::from(0);
    expect(zero.has_value(), "zero is a valid score");

    const auto hundred = grades::Score::from(100);
    expect(hundred.has_value(), "one hundred is a valid score");

    expect(!grades::Score::from(-1), "negative score is rejected");
    expect(!grades::Score::from(101), "score above one hundred is rejected");

    const auto fifty_nine = grades::Score::from(59);
    expect(fifty_nine && !fifty_nine->passed(), "59 does not pass");

    const auto sixty = grades::Score::from(60);
    expect(sixty && sixty->passed(), "60 passes by default");

    return failures == 0 ? 0 : 1;
}
```

无需为了测试而把 `value_` 改成 `public`。通过公开工厂和查询函数，就能检查外部真正依赖的行为。直接测试私有实现会让重构变得困难：行为没变，测试却因为内部结构变化而全部损坏。

## 边界条件不是随便多写几组数字

边界通常来自接口规则和数据结构。对 `Score::from`，等价区域可以分为：

```text
小于 0 | 0 到 100 | 大于 100
```

最值得先检查的是边界本身及其两侧：`-1`、`0`、`100`、`101`。此外再选一两个区域内部的代表值即可。把 `1` 到 `99` 全部列出来，并不会自动让测试更有价值。

常见边界还包括：

- 空容器、单元素容器和较大容器；
- 空字符串、只有空白、包含非 ASCII 字符；
- 第一个元素、最后一个元素和不存在的元素；
- 重复值、最大最小值、溢出附近；
- 文件不存在、内容截断、权限不足。

从契约推导等价类和边界，比只测试自己想到的“典型输入”更可靠。

## 失败路径也要能观察

上一章的 `read_student` 接收 `std::istream&`，这使测试不必真的等待键盘输入。`std::istringstream` 可以提供内存中的输入流：

```cpp
#include "grades/io.hpp"

#include <sstream>

void test_invalid_score() {
    std::istringstream input{"1001 Alice 130"};

    const auto student = grades::read_student(input);

    expect(!student, "student with an invalid score is rejected");
}
```

这不是为了测试而加入的特殊后门。让函数依赖抽象的 `std::istream`，本来就比把 `std::cin` 写死在函数内部更灵活：生产环境传 `std::cin` 或文件流，测试传字符串流。

如果采用异常接口，可以明确检查是否抛出预期的异常类型。不要只检查“随便抛了点什么”，也不要把整个测试包在一个巨大的 `try/catch` 中，以免真正的测试缺陷被误判成预期失败。

## 用 CTest 组织测试可执行文件

在根 `CMakeLists.txt` 中，上一节已经写下：

```cmake
include(CTest)

if(BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

接着创建 `tests/CMakeLists.txt`：

```cmake
add_executable(score_test score_test.cpp)
target_link_libraries(score_test PRIVATE grades_core)
enable_project_warnings(score_test)

add_executable(statistics_test statistics_test.cpp)
target_link_libraries(statistics_test PRIVATE grades_core)
enable_project_warnings(statistics_test)

add_test(NAME score_test COMMAND score_test)
add_test(NAME statistics_test COMMAND statistics_test)
```

重新配置、构建并测试：

```sh
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

也可以直接在构建目录运行：

```sh
ctest --test-dir build/debug --output-on-failure
```

CTest 是**测试驱动程序**，不是断言库或测试框架。它不知道 `expect`、测试用例分组和参数化测试，只负责发现由 `add_test` 注册的命令、运行它们并汇总结果。项目变大后可以使用 Catch2、GoogleTest 或 doctest 等框架编写测试，再继续让 CTest 统一运行它们。

测试代码也要启用与生产代码相近的警告，并链接真实的 `grades_core`。不要在测试目录复制一份被测实现，否则测试通过的可能是副本，而不是程序真正使用的代码。

## 测试替身只用在边界

假设成绩发布后要发送通知：

```cpp
class Notifier {
  public:
    virtual ~Notifier() = default;
    virtual void send(const Student& student) = 0;
};
```

测试时不应真的发邮件，可以传入一个记录调用的实现：

```cpp
class RecordingNotifier : public Notifier {
  public:
    void send(const Student& student) override {
        notified_ids.push_back(student.id);
    }

    std::vector<int> notified_ids;
};
```

这样的对象统称为**测试替身**。它可以代替网络、时钟、随机数发生器、文件系统等慢、不稳定或有外部副作用的边界。

不要因为“单元测试必须隔离”就模拟每一个类。大量 mock 往往把测试绑定到实现调用顺序，而不是业务结果。值对象、纯函数和内存中的普通容器直接使用真实实现通常更简单、更可信。

## 测试的层次

单元测试不是全部。项目通常还需要：

- **集成测试**：检查多个组件或与数据库、文件格式等边界能否协作；
- **端到端测试**：从程序入口模拟完整使用流程；
- **回归测试**：发现 bug 后先固定能复现它的输入，防止以后再次出现。

越靠近端到端，覆盖的真实路径越完整，但运行更慢、失败原因也更难定位。好的测试组合通常有许多快速的小测试，以及少量覆盖关键路径的较大测试。

## 测试不能证明没有 bug

测试只检查运行到的样例。未定义行为可能在当前机器上“通过”，竞态问题可能一百次才出现一次，未覆盖路径仍然未知。因此测试应和编译器警告、静态分析、sanitizer、代码评审共同工作。

同样，不要盲目追求覆盖率数字。覆盖一行只说明它执行过，不说明所有结果都被检查。覆盖率适合帮助发现从未触达的区域，不适合作为测试质量的唯一目标。

## 小结

- 自动化测试以可重复方式调用接口、检查行为，并用退出状态报告结果
- 优先从纯函数、公开契约和类的不变式开始测试
- 从等价类和规则推导边界值，同时覆盖成功与失败路径
- 可注入的输入流等依赖让生产代码更灵活，也让测试更容易
- CTest 负责运行测试命令，测试框架负责组织断言和用例
- 测试替身适合隔离外部边界，不应把每个普通对象都模拟掉
- 测试不能取代警告、静态分析、运行时检查和代码评审
