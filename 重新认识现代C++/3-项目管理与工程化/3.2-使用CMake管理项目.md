# 3.2 使用 CMake 管理项目

上一节中我们尝试了手动编译一个多文件 C++ 项目。但那十分繁琐，其中有很多细节，例如程序由哪些源文件组成、头文件在哪里、使用什么语言标准、目标之间如何依赖，都需要手动管理。所以，构建系统的工作，就是把这以整套关系写成可重复执行的规则，自动化处理。

我们将会使用 [CMake](https://cmake.org/) 和 [Ninja](https://ninja-build.org/)。其中，CMake 是**构建系统生成器**（build system generator），负责描述项目如何构建，并生成具体构建系统所需的配置文件。

Ninja 是**构建执行工具**（build system），负责按照构建规则实际执行编译、链接等操作。类似的还有 GNU Make、MSBuild、Xcode Build System 等。

大致的流程是，CMake 读取项目中的 `CMakeLists.txt`，为 Ninja 生成构建规则并启动 Ninja。Ninja 根据构建规则调用编译器与链接器，生成产物。

## 安装 CMake 与 Ninja

在 [0.2 节](../0-在一切开始之前/0.2-Windows上的C++工具链) 我们已经介绍了如何在 Windows 上安装 MSYS2 UCRT64 环境。打开 MSYS2 UCRT64 终端环境，使用下面的命令安装 CMake 和 Ninja：

```sh
pacman -S --needed mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja
```

使用如下命令检查版本：

```sh
cmake --version
ninja --version
```

如果安装正常，应该可以看到形如这样的输出：

```ansi

$ cmake --version

CMake suite maintained and supported by Kitware (kitware.com/cmake).

[32mlinho@LinhosPC[0m [35mUCRT64[0m [33m~[0m
$ ninja --version
1.13.2
```

本套笔记以 CMake 3.25 版本为最低要求。

## 第一次配置、构建和运行

在项目根目录创建 `CMakeLists.txt`，填入下面内容：

```cmake
cmake_minimum_required(VERSION 3.25)

project(grades VERSION 0.1.0 LANGUAGES CXX)

add_library(grades_core
    src/io.cpp
    src/student.cpp
)

target_compile_features(grades_core PUBLIC cxx_std_20)
target_include_directories(grades_core PUBLIC include)

add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app PRIVATE grades_core)
```

我们稍后再来介绍其中每一条的含义。

首次构建需要执行**配置命令**：

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
```

这会配置并生成构建文件，执行后在根目录下生成 `build` 文件夹，其中就包含了 Ninja 所需的规则 `build.ninja`。命令中：

- `-S .` 指定源码目录；
- `-B build` 指定构建目录；
- `-G Ninja` 选择生成器；
- `CMAKE_BUILD_TYPE=Debug` 选择单配置生成器的构建类型。

一般来说配置只需要执行一次。后续修改 `.cpp` 和 `.hpp` 代码之后不需要重新配置。如果修改 `CMakeLists.txt`，一般会自动触发重新配置。

配置完成后执行**构建命令**：

```sh
cmake --build build
```

执行后，CMake 会调用 Ninja，Ninja 根据 `build.ninja` 中的规则调用编译器编译 `.cpp` 文件，再调用链接器生成最终 `.exe` 文件。此时，产物位于 `build` 目录下，名为 `grades_app.exe`。从终端启动它：

```sh
./build/grades_app.exe
```

就可以看到程序输出并进行交互了。此后修改代码，只需要重新执行构建命令，即可自动完成项目编译和链接，生成新的 `grades_app.exe`。各个编译模块的产物会缓存，每次只会编译改动过的部分，对于大型项目可以节省不少时间。

## 详解 `CMakeLists.txt`

现在我们回头再来看这段 `CMakeLists.txt`：

```cmake :line-numbers
cmake_minimum_required(VERSION 3.25)

project(grades VERSION 0.1.0 LANGUAGES CXX)

add_library(grades_core
    src/io.cpp
    src/student.cpp
)

target_compile_features(grades_core PUBLIC cxx_std_20)
target_include_directories(grades_core PUBLIC include)

add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app PRIVATE grades_core)
```

第 1 行 `cmake_minimum_required` 指定项目要求的最低 CMake 版本。CMake 在长期演进过程中，有些行为发生过变化。为了避免老项目升级 CMake 后行为突然改变，CMake 使用策略版本（Policy Version）机制兼容旧行为。CMake 会根据设置的最低版本设置策略版本，例如这里 CMake 就会按 3.25 版本的行为工作。

第 3 行 `project` 声明项目的基本信息。其中，`grades` 是项目名称，`VERSION 0.1.0` 是项目版本，`LANGUAGES CXX` 表示启用 C++ 语言支持。

CMake 本身并不局限于 C++，它还支持 C、CUDA、Fortran、ASM 等语言。如果这里写 `LANGUAGES C CXX`，就会同时启用 C 和 C++。CMake 会根据启用的语言检测相应的编译器，并设置相关变量。

第 5 行 `add_library` 是第一个创建构建目标的命令。它表示创建一个名为 `groudes_core` 的库，源文件包括 `src/io.cpp` 和 `src/io.cpp`。这里的 `groudes_core` 库是一个**目标**（target）。目标是 CMake 中承载源文件、编译选项、头文件路径和依赖关系的基本单位，使用 `target_*` 命令描述。接下来 10、11 两行 `target_*` 就描述了其配置。

第 10 行 `target_compile_features(grades_core PUBLIC cxx_std_20)` 表示目标 `grades_core` 需要支持 C++20，此配置以 `PUBLIC` 模式传播。CMake 会根据编译器情况自动添加类似 `-std=c++20` 这样的编译器选项。





- `grades_core` 是库目标，保存成绩程序的领域逻辑；
- `grades_app` 是可执行目标，只负责程序入口；
- `grades_app` 链接 `grades_core`，因此能使用它的实现和使用要求。

## 依赖关系会传播

`target_include_directories` 和 `target_link_libraries` 中的 `PUBLIC`、`PRIVATE`、`INTERFACE` 描述的是**使用要求如何传播**：

| 关键字      | 当前目标使用 | 依赖当前目标的目标使用 |
| ----------- | ------------ | ---------------------- |
| `PRIVATE`   | 是           | 否                     |
| `PUBLIC`    | 是           | 是                     |
| `INTERFACE` | 否           | 是                     |

`grades_core` 的公开头文件位于 `include`，而 `main.cpp` 也要包含这些头文件，所以这里使用 `PUBLIC`：

```cmake
target_include_directories(grades_core PUBLIC include)
```

假设 `grades_core` 的实现使用一个日志库，但它的公开头文件完全没有暴露日志库类型，那么这个依赖通常是 `PRIVATE`：

```cmake
target_link_libraries(grades_core PRIVATE some_logging_library)
```

如果公开头文件中出现了某依赖的类型，使用者编译自己的源码时也需要那项依赖，它通常应当是 `PUBLIC`。`INTERFACE` 常用于只有头文件的库，或专门聚合编译选项的目标。

这三个词不是“重要程度”，也不是“是否允许外部调用”。判断时只问：当前目标编译时是否需要；使用者编译时是否也需要。

## 把警告附着到目标

不同编译器的警告选项不同，可以按编译器选择：

```cmake
if(MSVC)
    target_compile_options(grades_core PRIVATE /W4 /permissive-)
    target_compile_options(grades_app PRIVATE /W4 /permissive-)
else()
    target_compile_options(grades_core PRIVATE -Wall -Wextra -Wpedantic)
    target_compile_options(grades_app PRIVATE -Wall -Wextra -Wpedantic)
endif()
```

警告属于项目自身的编译过程，因此使用 `PRIVATE`。不要轻易把 `-Werror` 写成库的 `PUBLIC` 使用要求，否则使用者可能因为另一款编译器的新警告而无法构建。是否在 CI 中把项目自身的警告视为错误，可以由项目策略决定。

当多个目标需要相同设置时，可以写一个小函数，避免复制：

```cmake
function(enable_project_warnings target_name)
    if(MSVC)
        target_compile_options(${target_name} PRIVATE /W4 /permissive-)
    else()
        target_compile_options(${target_name} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endfunction()

enable_project_warnings(grades_core)
enable_project_warnings(grades_app)
```

## 不要把源文件自动全部抓进来

下面的写法看起来省事：

```cmake
file(GLOB SOURCES CONFIGURE_DEPENDS "src/*.cpp")
add_executable(grades_app ${SOURCES})
```

但明确列出源文件通常更适合项目维护。`CMakeLists.txt` 本身就是目标组成的清单，代码评审时能看到文件何时加入或移除，也不会误把临时源码编进目标。文件很多时可以拆分子目录和多个目标，而不是用一个巨大通配符掩盖结构。

## 用 Presets 保存共同配置

每次输入一长串参数既麻烦又容易产生机器间差异。`CMakePresets.json` 可以把项目共享的配置保存下来：

```json
{
  "version": 6,
  "cmakeMinimumRequired": {
    "major": 3,
    "minor": 25,
    "patch": 0
  },
  "configurePresets": [
    {
      "name": "debug",
      "displayName": "Debug with Ninja",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/debug",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    },
    {
      "name": "release",
      "inherits": "debug",
      "displayName": "Release with Ninja",
      "binaryDir": "${sourceDir}/build/release",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release"
      }
    }
  ],
  "buildPresets": [
    {
      "name": "debug",
      "configurePreset": "debug"
    },
    {
      "name": "release",
      "configurePreset": "release"
    }
  ]
}
```

此后命令变为：

```sh
cmake --preset debug
cmake --build --preset debug
```

`CMakePresets.json` 应提交到版本控制，保存团队共同配置。个人机器专属且不适合共享的覆盖项可以放在 `CMakeUserPresets.json`，并把后者加入 `.gitignore`。

Preset 不是构建产物。它是“怎样配置项目”的可读声明，IDE 和命令行也可以共同使用。

## 为测试保留入口

CMake 自带的测试驱动程序叫 CTest。现在先在根 `CMakeLists.txt` 中建立结构：

```cmake
include(CTest)

if(BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

`include(CTest)` 会提供 `BUILD_TESTING` 选项并启用测试。真正的测试目标和 `add_test` 留到 3.4 节。需要关闭测试时可以配置 `-DBUILD_TESTING=OFF`，而不是编辑源码。

还可以为 preset 增加测试入口：

```json
"testPresets": [
  {
    "name": "debug",
    "configurePreset": "debug",
    "output": { "outputOnFailure": true }
  }
]
```

以后就能统一运行：

```sh
ctest --preset debug
```

## 一份完整的当前配置

```cmake
cmake_minimum_required(VERSION 3.25)

project(grades VERSION 0.1.0 LANGUAGES CXX)

function(enable_project_warnings target_name)
    if(MSVC)
        target_compile_options(${target_name} PRIVATE /W4 /permissive-)
    else()
        target_compile_options(${target_name} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endfunction()

add_library(grades_core
    src/io.cpp
    src/student.cpp
)
target_compile_features(grades_core PUBLIC cxx_std_20)
target_include_directories(grades_core PUBLIC include)
enable_project_warnings(grades_core)

add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app PRIVATE grades_core)
enable_project_warnings(grades_app)

include(CTest)
if(BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

## 小结

- CMake 描述并生成构建过程，不是编译器，也不是包管理器
- 用目标表达可执行文件、库及它们之间的依赖
- 优先使用 `target_*` 命令，让配置附着于需要它的目标
- `PUBLIC`、`PRIVATE`、`INTERFACE` 描述使用要求是否作用和传播
- 源码与构建目录分离，构建产物不进入版本控制
- `CMakePresets.json` 保存可共享、可重复的配置方式
- CTest 可以加入同一套目标图，后续测试无需另造一套构建流程
