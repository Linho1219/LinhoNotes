# 3.2 使用 CMake 管理项目

上一节中我们尝试了手动编译一个多文件 C++ 项目。但那十分繁琐，其中有很多细节，例如程序由哪些源文件组成、头文件在哪里、使用什么语言标准、目标之间如何依赖，都需要手动管理。所以，构建系统的工作，就是把这以整套关系写成可重复执行的规则，自动化处理。

我们将会使用 [CMake](https://cmake.org/) 和 [Ninja](https://ninja-build.org/)。其中，CMake 是**构建系统生成器**（build system generator），负责描述项目如何构建，并生成具体构建系统所需的配置文件。

Ninja 是**构建执行工具**（build system），负责按照构建规则实际执行编译、链接等操作。类似的还有 GNU Make、MSBuild、Xcode Build System 等。

大致的流程是，CMake 读取项目中的 `CMakeLists.txt`，为 Ninja 生成构建规则并启动 Ninja。Ninja 根据构建规则调用编译器与链接器，生成产物。

## 安装 CMake 与 Ninja

在 [0.2 节](../0-在一切开始之前/0.2-Windows上的C++工具链) 我们已经介绍了如何在 Windows 上安装 MSYS2 UCRT64 环境。打开 MSYS2 UCRT64 终端环境，使用下面的命令安装 CMake 和 Ninja：

```sh
pacman -S --needed mingw-w64-ucrt-x86_64-cmake mingw-w64-ucrt-x86_64-ninja
```

使用如下命令检查版本：

```sh
cmake --version
ninja --version
```

如果安装正常，应该可以看到形如这样的输出：

```ansi
[32mlinho@LinhosPC[0m [35mUCRT64[0m [33m~[0m
$ cmake --version
cmake version 4.4.3

CMake suite maintained and supported by Kitware (kitware.com/cmake).

[32mlinho@LinhosPC[0m [35mUCRT64[0m [33m~[0m
$ ninja --version
1.13.2
```

本套笔记以 CMake 3.25 版本为最低要求。

## 第一次配置、构建和运行

在项目根目录创建 `CMakeLists.txt`，填入下面内容：

```cmake
cmake_minimum_required(VERSION 3.25)

project(grades VERSION 0.1.0 LANGUAGES CXX)

add_library(grades_core
    src/io.cpp
    src/student.cpp
)

target_compile_features(grades_core PUBLIC cxx_std_20)
target_include_directories(grades_core PUBLIC include)

add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app PRIVATE grades_core)
```

我们稍后再来介绍其中每一条的含义。

首次构建需要执行**配置命令**：

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
```

这会配置并生成构建文件，执行后在根目录下生成 `build` 文件夹，其中就包含了 Ninja 所需的规则 `build.ninja`。命令中：

- `-S .` 指定源码目录；
- `-B build` 指定构建目录；
- `-G Ninja` 选择生成器；
- `CMAKE_BUILD_TYPE=Debug` 选择单配置生成器的构建类型。

一般来说配置只需要执行一次。后续修改 `.cpp` 和 `.hpp` 代码之后不需要重新配置。如果修改 `CMakeLists.txt`，一般会自动触发重新配置。

配置完成后执行**构建命令**：

```sh
cmake --build build
```

执行后，CMake 会调用 Ninja，Ninja 根据 `build.ninja` 中的规则调用编译器编译 `.cpp` 文件，再调用链接器生成最终 `.exe` 文件。此时，产物位于 `build` 目录下，名为 `grades_app.exe`。从终端启动它：

```sh
./build/grades_app.exe
```

就可以看到程序输出并进行交互了。此后修改代码，只需要重新执行构建命令，即可自动完成项目编译和链接，生成新的 `grades_app.exe`。各个编译模块的产物会缓存，每次只会编译改动过的部分，对于大型项目可以节省不少时间。

顺带一提，`build` 目录可以从 `CMakeLists.txt` 生成，包含各种中间和产物文件，所以应该加入到 `.gitignore`。

## 详解 `CMakeLists.txt`

现在我们回头再来看这段 `CMakeLists.txt`：

```cmake :line-numbers
cmake_minimum_required(VERSION 3.25)

project(grades VERSION 0.1.0 LANGUAGES CXX)

add_library(grades_core
    src/io.cpp
    src/student.cpp
)

target_compile_features(grades_core PUBLIC cxx_std_20)
target_include_directories(grades_core PUBLIC include)

add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app PRIVATE grades_core)
```

第 1 行 `cmake_minimum_required(VERSION 3.25)` 指定项目要求的最低 CMake 版本。CMake 在长期演进过程中，有些行为发生过变化。为了避免老项目升级 CMake 后行为突然改变，CMake 使用策略版本（Policy Version）机制兼容旧行为。CMake 会根据设置的最低版本设置策略版本，例如这里 CMake 就会按 3.25 版本的行为工作。

第 3 行 `project(grades VERSION 0.1.0 LANGUAGES CXX)` 声明项目的基本信息。其中，`grades` 是项目名称，`VERSION 0.1.0` 是项目版本，`LANGUAGES CXX` 表示启用 C++ 语言支持。CMake 本身并不局限于 C++，它还支持 C、CUDA、Fortran、ASM 等语言。比如，如果这里写 `LANGUAGES C CXX`，就会同时启用 C 和 C++。CMake 会根据启用的语言检测相应的编译器，并设置相关变量。

第 5 行 `add_library(grades_core src/io.cpp src/student.cpp)` 是第一个创建构建目标的命令。它表示创建一个名为 `groudes_core` 的库，源文件包括 `src/io.cpp` 和 `src/io.cpp`。

这里的 `groudes_core` 库是一个**目标**（target）。目标是 CMake 中承载源文件、编译选项、头文件路径和依赖关系的基本单位，使用 `target_*` 命令描述。接下来 10、11 两行 `target_*` 就描述了其配置。

第 10 行 `target_compile_features(grades_core PUBLIC cxx_std_20)` 表示目标 `grades_core` 需要支持 C++20，此属性以 `PUBLIC` 范围传播。CMake 会根据编译器情况自动添加类似 `-std=c++20` 这样的编译器选项。

CMake 有三种常见的属性传播范围：

| 关键字      | 当前目标使用 | 依赖当前目标的目标使用 |
| ----------- | ------------ | ---------------------- |
| `PRIVATE`   | 是           | 否                     |
| `PUBLIC`    | 是           | 是                     |
| `INTERFACE` | 否           | 是                     |

为什么 C++ 标准需要传播？如果新语法、新特性只在目标内部使用，那此时确实不需要传播，应该为 `PRIVATE`。而如果对外暴露的 `.hpp` 中包含了新特性，此时其他目标在包含它的时候也必须使用支持新标准的编译器配置，例如此处的 `PUBLIC` 就表示依赖目标 `grades_core` 的其他目标也必须支持 C++20 或更新的标准。`INTERFACE` 则常用于只有头文件的库。

第 11 行的 `target_include_directories(grades_core PUBLIC include)` 也是目标属性，表示目标 `grades_core` 需要在目录 `include` 中搜索头文件，此属性以 `PUBLIC` 范围传播。这很好理解，这样所有使用它的目标也会在其中搜索头文件，代码中就可以写 `#include "grades/student.hpp"` 了。

第 13 行的 `add_executable(grades_app src/main.cpp)` 类似于前面的 `add_library`，也是创建目标，不过这次创建的是可执行文件目标。这里表示创建一个名为 `grades_app` 的可执行程序，入口相关的源文件是 `src/main.cpp`。所以最终会生成 `grades_app.exe`。

最后一行 `target_link_libraries(grades_app PRIVATE grades_core)` 表示 `grades_app` 依赖 `grades_core`。这样刚才 `grades_core` 上配置的 C++ 标准和头文件搜索路径就传播到了 `grades_app` 上，编译后两个目标会链接在一起。这里使用 `PRIVATE` 是因为 `grades_app` 是最终的可执行文件，没有其他目标需要继承这个依赖。

总结一下，这份 `CMakeLists.txt` 规定了：

- 库目标 `grades_core`
  - 包含源文件：
    - `src/io.cpp`
    - `src/student/cpp`
  - 使用 C++20，`PUBLIC` 向下游传播
  - 头文件目录 `include/`，`PUBLIC` 向下游传播
- 可执行文件目标 `grades_app`
  - 包含源文件：`src/main.cpp`
  - 依赖目标 `grades_core`，`PRIVATE` 不传播
    - 继承 C++20
    - 继承头文件目录 `include/`

## 根据编译器动态配置

你可能已经注意到，前面 `CMakeLists.txt` 里的内容似乎不像 JSON 或者 YAML 那样的标记语言，相反更像某种编程语言，定义各个配置项的形式与调用函数时一样的。事实上，其中的内容就是一种脚本语言，CMake 脚本。其中可以定义变量和函数，也有逻辑分支。不过考虑到这不是本笔记的主要内容，这部分我们结合实例，蜻蜓点水般过一下，就不深入了。如果有兴趣，可以自行查阅资料。

一个常见的需求是，不同编译器的警告选项不同，我们希望可以按编译器选择。那么可以这样写：

```cmake
if(MSVC)
    target_compile_options(grades_core PRIVATE /W4 /permissive-)
    target_compile_options(grades_app PRIVATE /W4 /permissive-)
else()
    target_compile_options(grades_core PRIVATE -Wall -Wextra -Wpedantic)
    target_compile_options(grades_app PRIVATE -Wall -Wextra -Wpedantic)
endif()
```

警告属于项目自身的编译过程，因此应该使用 `PRIVATE`。

当多个目标需要相同设置时，可以写一个小函数，避免复制。CMake 脚本在 `if` 和 `while` 命令中，变量直接写名字即可调用，而在其他地方使用 `${}` 语法调用变量。

```cmake
function(enable_project_warnings target_name)
    if(MSVC)
        target_compile_options(${target_name} PRIVATE /W4 /permissive-)
    else()
        target_compile_options(${target_name} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endfunction()

enable_project_warnings(grades_core)
enable_project_warnings(grades_app)
```

## 基于目标的 CMake 与传统 CMake

我们刚才介绍的写法称为 Target-based CMake（基于目标的 CMake），属性设置在各个具体的构建目标上，并通过 `PRIVATE`、`PUBLIC`、`INTERFACE` 三种模式进行传播。

传统写法

```cmake
cmake_minimum_required(VERSION 3.10)

project(grades VERSION 0.1.0 LANGUAGES CXX)

# 全局设置 C++ 标准
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# 全局设置头文件搜索目录
include_directories(include)

# 全局设置编译选项
if(MSVC)
    add_compile_options(/W4 /permissive-)
else()
    add_compile_options(-Wall -Wextra -Wpedantic)
endif()

add_library(grades_core
    src/io.cpp
    src/student.cpp
)
add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app grades_core)
```

这里的各个配置项全部定义在全局，与目标无关。甚至还可以直接不再定义 `grades_core`，使用通配符把所有 `.cpp` 文件都塞入一个目标 `grades_app`，这样也不需要链接两个目标：

```cmake
add_library(grades_core#[!code --]
    src/io.cpp#[!code --]
    src/student.cpp#[!code --]
)#[!code --]
add_executable(grades_app src/main.cpp)#[!code --]
target_link_libraries(grades_app grades_core)#[!code --]

# 搜索 src 目录下的所有 .cpp 文件，存入变量 SOURCES#[!code ++]
file(GLOB SOURCES CONFIGURE_DEPENDS "src/*.cpp")#[!code ++]
add_executable(grades_app ${SOURCES})#[!code ++]
```

把配置全部扔到全局确实很方便，在我们的示例项目中也可以工作，不过现在一般不推荐这样做。这是因为基于目标的配置方式提供更细粒度的管理，而传统的全局写法在复杂的多目标项目时容易出现冲突。通配符现在一般也不推荐使用，这是因为明确列出源文件更适合项目维护，代码评审时能看到文件何时加入或移除，也不容易误把临时源码编进目标。传统写法只需要认识即可，不必完全掌握。

## CMake Presets

CMake 支持从命令行参数定义变量，以 `D` 开头。例如前面传统 CMake 配置中的 `set(CMAKE_CXX_STANDARD 20)` 就可以直接在命令行参数中写 `-DCMAKE_CXX_STANDARD=20`。这样一来，很多配置项可以外置到命令行中，实现一份 `CMakeLists.txt` 配合不同命令来适配不同场景。例如，选用不同的构建类型（debug / release），针对不同平台指定不同的编译器和构建执行工具，或者在本地和 CI 环境中使用不同的配置项。

但这也造成一个问题，随着命令行配置越来越多，命令也会越来越长，也更容易出错。在 CI 或者团队协作场景下也会很麻烦。

为此 CMake 从 3.19 版本开始提供了 CMake Presets，根目录的一个 `CMakePresets.json` 文件把配置保存下来，例如：

```json
{
  "version": 6,
  "cmakeMinimumRequired": {
    "major": 3,
    "minor": 25,
    "patch": 0
  },
  "configurePresets": [
    {
      "name": "debug",
      "displayName": "Debug with Ninja",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/debug",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"
      }
    },
    {
      "name": "release",
      "inherits": "debug",
      "displayName": "Release with Ninja",
      "binaryDir": "${sourceDir}/build/release",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release"
      }
    }
  ],
  "buildPresets": [
    {
      "name": "debug",
      "configurePreset": "debug"
    },
    {
      "name": "release",
      "configurePreset": "release"
    }
  ]
}
```

此后命令变为：

```sh
cmake --preset debug
cmake --build --preset debug
```

`CMakePresets.json` 提交到 git，保存团队共享配置。另外，CMake 还支持用 `CMakeUserPresets.json` 保存个人专属的配置，后者应该加入 `.gitignore`。

## 小结

::: details 完整 `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.25)

project(grades VERSION 0.1.0 LANGUAGES CXX)

function(enable_project_warnings target_name)
    if(MSVC)
        target_compile_options(${target_name} PRIVATE /W4 /permissive-)
    else()
        target_compile_options(${target_name} PRIVATE -Wall -Wextra -Wpedantic)
    endif()
endfunction()

add_library(grades_core
    src/io.cpp
    src/student.cpp
)
target_compile_features(grades_core PUBLIC cxx_std_20)
target_include_directories(grades_core PUBLIC include)
enable_project_warnings(grades_core)

add_executable(grades_app src/main.cpp)
target_link_libraries(grades_app PRIVATE grades_core)
enable_project_warnings(grades_app)

include(CTest)
if(BUILD_TESTING)
    add_subdirectory(tests)
endif()
```

:::

- CMake 描述并生成构建过程
- 用目标表达可执行文件、库及它们之间的依赖
- 优先使用 `target_*` 命令，让配置定义在目标上
- `PUBLIC`、`PRIVATE`、`INTERFACE` 描述配置传播模式
- 源码与构建目录分离，构建产物不进入版本控制
- `CMakePresets.json` 保存可共享、可重复的配置方式

延伸阅读：[CMake 官方教程](https://cmake.org/cmake/help/latest/guide/tutorial/)。
